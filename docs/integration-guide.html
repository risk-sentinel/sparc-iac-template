SPARC · Integration guide

Integrating a team and a pipeline into SPARC

Two things connect to SPARC, and they connect differently. People arrive through your identity provider and get authority derived from their group grants. Pipelines arrive through a service account token and push evidence over the API. Both attach to the same thing — an authorization boundary that has to exist first — and that boundary has to be modelled before the evidence means anything: what you inherit from the platform beneath you, and which components you owe a definition for.

The shape of it

Nothing connects to SPARC in the abstract — it connects to a boundary. Create that first, then the two tracks can run independently and in either order.

Before you connect anything

These are prerequisites in the strict sense — each one has to exist before the next means anything, and a grant naming something that does not exist is recorded and surfaced, never auto-created. That restraint is deliberate: auto-creation would let your identity provider mint tenants.

  1. Create the Organization. Done in-app by an instance admin.
  2. Create the Authorization Boundary beneath it. This is the unit everything else scopes to — memberships, evidence, SSPs, assessment results.
  3. Define the roles and what each may do. SPARC owns what a role means; the IdP only ever answers whether a person holds it.
  4. Choose the API auth mode. SPARC_API_AUTH decides which token types the server will accept at all — get this wrong and every pipeline call fails identically regardless of the token.

The two tracks

These are parallel, not sequential. Neither blocks the other once the boundary exists.

Track A · People

Onboard the team

  1. Create an IdP group per role you want to grant.
  2. Name it with the fully qualified convention — sparc:boundary:org:boundary:role, or sparc:org:org:role for org scope.
  3. Add people to the group. Nothing is pushed to SPARC.
  4. They log in. SPARC reads the grants from the configured claim and derives their access for that session.
  5. Unmatched grants land in an admin queue rather than failing the login.

Track B · Pipeline

Connect the pipeline

  1. Go to Admin → Service Accounts and create one per pipeline.
  2. Scope it: restrict to the endpoints it needs, and to your runner CIDR range.
  3. Copy the token — prefix sparc_sa_ — and store it as a CI secret.
  4. Send it as a bearer token on every request.
  5. Push results at the end of your scan job.

Why entitlement is derived, not synced

A person's authority comes from the grants presented at that login — grants are never written into SPARC and later diffed. That removes the destructive revoke step, and with it the failure mode where an IdP misconfiguration becomes a customer-wide outage. Remove someone from a group and the entitlement simply does not materialise next login; restore it and recovery is automatic, with no operator action.

What you inherit, and what you own

Your system does not implement every control. It runs on top of an already-authorized provider, and that relationship has a direction: yours is the leveraging system, the cloud provider's authorization is the leveraged one. Every control in your baseline lands in one of three buckets, and getting the split right is what stops you writing implementation statements for things you do not control.

Of 370 HIGH baseline controls, 37 are inherited, 18 are shared, and 315 are system-specific.

How the relationship is expressed today

In the SPARC SSPs the leveraged authorization is carried by components typed leveraged-authorization — one for the inherited set, one for the shared set — sitting alongside the 17 service components that make up the system itself.

Three gaps in the current wiring

The dedicated OSCAL assembly is empty. system-implementation.leveraged-authorizations has zero entries in all three SSPs, so there is no party-uuid and no date-authorized naming which authorization is being leveraged. A reviewer can see that you inherit, but not from what.

The inheritance CDEFs are orphaned. The SSPs reference aws-inherited.json and aws-shared.json zero times — the same control sets are restated as SSP components instead, so the two copies can drift apart silently.

21 of the 58 inherited controls fall outside the HIGH baseline you are assessed against. They are not wrong, but they are not load-bearing either, and counting all 58 as coverage overstates it.

Which components need a CDEF

The rule is mechanical, which is what makes it auditable: one CDEF per distinct infrastructure component, mirroring the Terraform that builds it. The CDEF directory shadows the deployment pattern — AWS/CDEF/ECS/ alongside AWS/ECS/ — so a reviewer can walk the modules and the components side by side.

Deriving the list for a new pattern:

  1. List the components the pattern actually deploys. For ECS Fargate that is VPC/networking, ALB, the Fargate service, RDS, IAM, KMS, S3, Secrets Manager, CloudWatch, Config, GuardDuty, ECR, ACM, Route 53, SNS, SES and the pipeline itself — 18 CDEFs.
  2. Drop what you do not run. The EC2 pattern has no ecs-fargate CDEF and gains ebs and elasticache. A CDEF for a component you do not deploy is a claim you cannot evidence.
  3. Map each component's controls to the baseline, keyed by NIST control ID.
  4. Check for orphans in both directions — a Terraform module with no CDEF is an unmapped component; a CDEF with no module is a stale claim.

Vendor CDEFs arrive in another dialect — SPARC translates them

CDEFs published by AWS are keyed to AWS Security Hub identifiers — S3.1, S3.10, IAM.4 — not NIST 800-53 control IDs. You do not have to re-key them by hand. On import, SPARC enriches each Security-Hub-shaped control to NIST 800-53 through a two-hop chain: a direct lookup first, and failing that a hop via the control's AWS Config rule. Anything still unmatched is reported rather than silently dropped, and rake mappings:coverage_report tells you the direct, chained and unmapped counts against your live data.

Once controls are NIST-keyed, the control-mappings API crosswalks onward to whatever framework the assessment needs — Rev 4 to Rev 5, FedRAMP, ISO 27001. Curating a Config-rule mapping once benefits every Security Hub control referencing that rule on the next import, so the mapping effort compounds instead of repeating per service.

The shape of a push

Evidence accepts multipart/form-data when there is a file, or application/json for metadata only.

# at the end of your scan job
curl -sS -X POST "$SPARC_URL/api/v1/evidences" \
  -H "Authorization: Bearer $SPARC_SA_TOKEN" \
  -F "evidence[authorization_boundary_id]=$BOUNDARY_ID" \
  -F "evidence[title]=Nightly container scan" \
  -F "evidence[file]=@results.hdf.json"

Confirming it worked

  • People: the person signs in and sees the boundary. If they sign in but see nothing, check the admin unmatched-grant queue — that is where a misspelled group name surfaces.
  • Pipeline: the record appears under the boundary and the job exits non-zero on failure. Assert on the HTTP status in CI; a silent 401 that never fails the build is the usual way a broken integration goes unnoticed for weeks.

Three things that bite

Wrong auth mode. In oidc mode a perfectly valid service-account token is rejected. Production wants hybrid.

Local login left enabled. If a person can also sign in with a local password, disabling them at the IdP is not a complete offboard. In an IdP-as-source-of-record deployment, local login should be break-glass only.

Grants that name nothing. A group naming an org, boundary or role that does not exist is skipped and recorded — the login still succeeds, so this fails quietly. Check the queue.
